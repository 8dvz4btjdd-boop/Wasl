### SEC-06 — قيد المصدر يقبل مسارات غير مؤهلة ويفقد الرابط النهائي — P2

- الدليل: `lib/ai/sources/allowlist.ts:9–19` يقبل HTTP وكل subdomain؛ `rejectReason:55–73` لا يستثني comments/assistant في dawa/islamic-content. `fetch.ts:40–46` لا يرفض userinfo أو non443 أو أقسام التعليقات. redirects محكومة بالنطاق وDNS (`229–245`) لكن `fetchOriginalSource` يعيد النص بلا URL نهائي (`272`)؛ `extendCitation:312–320` يعيد النص فقط؛ `readings.ts:90–109` يواصل نسبة المقطع إلى c.url الأصلي.
- المستوى: **مثبت باختبارات دوال فعلية مع DNS/transport mocks**: non443 ومسار comments وصلا إلى transport؛ redirect بين مصدرين مسموحين أضاف نصًا من الصفحة النهائية دون حفظ هويتها. لا يثبت ذلك وجود تعليق ضار على مصدر حقيقي أو SSRF مُستغل.
- نقاط قوة وحدود: HTTP يُرفض في الجلب نفسه، وكل DNS answers يجب أن تكون public، والنطاق الخارجي في redirect يُرفض، وحد800k bytes ومهلة10s موجودان. فحص DNS ثم fetch لا يربط الاتصال بالعنوان المفحوص؛ DNS rebinding خطر محتمل عند سيطرة مهاجم على hostname مسموح، وليس استغلالًا ثبت هنا.
- أقل معالجة: سجل source/section/work موحد يستخدمه البحث والجلب وcache؛ HTTPS بلا userinfo وبمنفذ443؛ حفظ finalURL/source identity والتحقق منهما قبل نسبة المقطع. رفض الأقسام غير المصدرية وإضافة اختبارات redirect وcache. إن بقي DNS guard، وثّق حد عدم pinning أو استخدم resolver/transport يربط العنوان.
- القبول: الأقسام المحظورة أو edition غير المسموحة لا تدخل عبر fetch/cache؛ تغيير المصدر بالredirect يعيد المصدر الصحيح أو يُرفض، والمقاطع لا تُنسب إلى المصدر الأول صامتًا.
- الجهد: 3–6 ساعات للسجل والرابط والاختبارات؛ resolver مضبوط قد يحتاج وقتًا إضافيًا. تفاصيل الاعتماد العلمي في مراجعة المصادر لتجنب التكرار.

## ضوابط جيدة ثبتت أو قُرئت

- SQL المحلي منع admin وغير المعيّن والمحظور من messages نفسها؛ لا يوجد viewer policy عام للرسائل بعد migration0005.
- draft البطاقة مخفية عن الداعية. تعديل النص وsource_message_ids وvisibility/accept_substitute بعد approval مرفوض في DB؛ draft جديدة لا تحل محل approved عند القراءة؛ expires_at يمنع viewer. هذه نتائج SQL فعلية، مع الاستثناء في مفاتيح العلاقة المذكور في SEC-04.
- `/api/ai/card` يتحقق ملكية conversation وعدد الاختيارات ثم يجلب IDs المختارة فقط قبل runAI (`route.ts:26–47`). `submitCard:52–65` يكرر تحقق الملكية. هذا تتبع للكود، لا إثبات جودة نموذج حي.
- secrets العمودان return_code_hash وreturn_code_salt ممنوع SELECT عليهما لأدوار العميل (`0002_identity.sql:67–72`)، وrelink/record_failure SERVICE-only. رمز49bit تقريبي وhash مملح وtimingSafeEqual، وقفل5 إخفاقات/15min موجود. لم أختبر brute force أو إنتاج Auth.
- `runAI` يفحص ai_enabled قبل cache. cache task/inputHash مستخدم الآن في classify وplan_queries فقط، وليس card/intake/tone. نقص org/model/prompt-version في المفتاح تحسين ضبط وتجدد P3، وليس تسربًا مثبتًا عند تطابق الإدخال الكامل. لا أستنتج تسربًا لمجرد كون cache مشتركة.
- مدخلات البطاقة المنقولة إلى ai_runs منقحة إلى أطوال ومراجع (`runAI:48–57`، `card.ts:34`) وtone persistOutput=false. plan_queries ما زال يحتفظ queries في output؛ حدود إرسال النص الخام إلى أدوات الويب موثقة ضمن مراجعة AI/المصادر الأخرى.
- لم تظهر أنماط مفاتيح Anthropic/JWT/AWS أو private key في الفحص الآلي للنصوص المتتبعة حتى1MB. هذه نتيجة أربعة patterns فقط، وليست ضمان خلو المستودع أو تاريخه من الأسرار. لم أطبع قيمًا أو أقرأ أسرار البيئة.
